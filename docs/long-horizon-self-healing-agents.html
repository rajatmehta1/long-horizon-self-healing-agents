Long-horizon agents need a memory of consequences

A prompt can produce an answer. A durable agent must survive process death, wait days for a person, retry unreliable systems, enforce non-negotiable policy, and resume without repeating side effects. This project shows the beginnings of that architecture through a customer-refund workflow.

01 / THE PROBLEM

An agent is not long-running because its prompt is long

The difficult part of agentic systems is not generating the next token. It is preserving intent and correctness across time, failure, and organizational boundaries.

Consider a refund request. The system must understand an unstructured complaint, join it with order facts, decide eligibility, apply financial limits, sometimes wait for a reviewer, call an unreliable payment gateway, and send a coherent response. A failure can occur between any two of those actions. The worker may restart after a model call but before its result is saved. The refund API may succeed while the network response disappears. A reviewer may answer tomorrow.

If this is implemented as a single agent loop, “try again” can mean “charge again,” “send again,” or “reason from a different state.” Reliability therefore belongs below the model, in a durable execution layer that records what happened and constrains what may happen next.

Core thesis: let models interpret and communicate; let deterministic code authorize; let durable orchestration remember.
02 / ARCHITECTURE

Three layers, three different kinds of authority

The repository separates the system into a CLI trigger, a Temporal workflow, Temporal activities, and small LangGraph agents. That separation is more important than the particular customer-support example: it creates explicit failure and trust boundaries.

Durable authority

Temporal workflow

Owns sequence, timers, retries, signals, and terminal outcomes. Its history is the source of truth for progress.

Cognitive capability

LangGraph agents

Classify complaints and draft messages inside activities. Their outputs are data, not permission.

Policy authority

Deterministic gates

Thresholds in ordinary code decide auto-approval, human review, or a hard stop.

External authority

Human signals

A reviewer can approve or reject without being coupled to a running worker process.

The implementation expresses these boundaries in its file structure:

app/
├── workflow.py          # durable control flow and policy gates
├── activities.py        # side effects and agent adapters
├── contracts.py         # typed payloads and thresholds
├── worker.py            # registers workflow + activities
├── trigger.py           # starts, signals, and queries
└── agents/
    ├── intake_agent.py      # LLM structured extraction
    ├── eligibility_agent.py # deterministic graph
    └── comms_agent.py       # bounded response generation
03 / DETERMINISM

Replay is the hidden contract

Temporal can reconstruct workflow state by replaying recorded history through workflow code. That only works when the workflow makes the same decisions from the same history.

This is why the project keeps model calls, UUID generation, external APIs, and changing clocks inside activities. The workflow itself compares recorded values against constants and chooses branches. On replay, Temporal does not need to ask the model again for already-completed activities; it supplies the result recorded in history.

# workflow.py — orchestration is deterministic
intake = await workflow.execute_activity(ingest_complaint, complaint, ...)
eligibility = await workflow.execute_activity(assess_eligibility, intake, ...)

amount = eligibility.refund_amount
if amount > POLICY_MAX_REFUND:
    return await policy_block(...)
if amount > AUTO_APPROVE_THRESHOLD:
    await workflow.wait_condition(lambda: self._approval is not None, ...)

There is a subtle design principle here: an LLM result becomes trustworthy workflow input only after it crosses a typed activity boundary and is recorded. Pydantic models such as IntakeResult and EligibilityResult make that boundary explicit. They reduce ambiguity, stabilize serialization, and give downstream policy code a constrained vocabulary.

04 / FAILURE SEMANTICS

Self-healing is recovery with invariants

The term self-healing is often used too loosely. Restarting a process is not enough. A useful definition is: the system can detect a recoverable failure, resume from durable state, retry according to policy, and preserve business invariants without manual reconstruction.

The repository defines two retry profiles. Standard activities get three attempts beginning at two seconds. Refund processing gets five attempts, exponential backoff, and a 30-second maximum interval. The distinction is healthy: retries are not a generic toggle; they are part of the semantics of each dependency.

_REFUND_RETRY = RetryPolicy(
    maximum_attempts=5,
    initial_interval=timedelta(seconds=4),
    backoff_coefficient=2.0,
    maximum_interval=timedelta(seconds=30),
)
Advanced caveat — retries are not idempotency. The demo fails before creating a refund, so retrying is safe. A real gateway can commit the refund and then lose the response. The next attempt could pay twice. Production code should send a stable idempotency key—usually derived from the workflow ID and business operation—and persist the provider’s response.

Failure classification comes before recovery

Transient transport errors deserve retry. Invalid payloads, policy violations, and missing orders usually do not. A mature system attaches explicit error types, non-retryable flags, timeouts, and escalation routes. Otherwise a “self-healing” loop can become a very durable denial-of-service attack against its own dependencies.

05 / HUMAN CONTROL

Humans are part of the protocol, not an exception path

Refunds above AUTO_APPROVE_THRESHOLD pause on workflow.wait_condition. The reviewer decision arrives as a Temporal signal carrying an approval bit, reviewer identity, and notes. A query exposes current status without mutating workflow state.

@workflow.signal
def human_approval(self, signal: HumanApprovalSignal) -> None:
    self._approval = signal

@workflow.query
def approval_status(self) -> str:
    if self._approval is None:
        return "AWAITING_HUMAN_REVIEW"
    return "APPROVED" if self._approval.approved else "REJECTED"

This is a control-plane design. The workflow can be waiting even when no worker is holding a thread, socket, or database lock. The signal becomes part of history, which makes the reviewer decision replayable and auditable. The timeout also has business meaning: after 90 seconds in this demo, the case transitions to TIMED_OUT_ESCALATED and the customer receives a different message.

For production, strengthen the signal boundary with authentication, role checks, duplicate-signal handling, decision versioning, and an immutable review record. “A signal was received” is not the same claim as “an authorized person approved the correct policy version.”

06 / STATE + POLICY

The workflow is an executable state machine

Enums in contracts.py name the observable outcomes, while branches in workflow.py define which transitions are possible. The policy maximum is a true hard stop: there is no model instruction capable of routing around it because no forward edge exists in code.

Notice the asymmetry: agents may propose structured facts, but code grants authority. The intake agent classifies issue_type and severity. The eligibility graph applies return-window rules. The workflow applies monetary thresholds. This is a practical form of capability containment: each component can influence only the decisions its contract permits.

Policy must be versioned with history

Long-lived workflows may outlive a code deployment. If thresholds change while old histories are replayed, branching behavior can diverge. Production Temporal applications should use workflow versioning or patching strategies and record the policy version used for each case. The rule is simple: old history must continue to mean what it meant when it was written.

07 / PRODUCTION READINESS

What this prototype proves—and what it does not

The current code is an effective architecture demonstration. It is not yet a deployable support platform. That distinction is useful because it produces a concrete hardening backlog.

Code-grounded issues to fix first: cmd_demo() uses ORD-… IDs while the data store uses ORDER-…; the fixed eligibility date is August 13, 2026 while comments and scenarios imply later dates; main.py is still the IDE sample; and no dependency manifest documents the runtime. These are small defects, but reproducibility is part of reliability.

Self-healing needs observability

A retry that eventually succeeds can still signal a degrading dependency. Track attempts per activity, end-to-end workflow latency, time spent awaiting humans, policy-block rates, model validation failures, and duplicate-suppression events. The most valuable metric is often not “workflow succeeded,” but “how much recovery work was required before it succeeded?”

08 / BUILD ROADMAP

Build the project piece by piece

The safest learning path is to add one reliability property at a time. Each stage should have a visible acceptance criterion before the next abstraction is introduced.

Define contracts before agents

Start with CustomerComplaint, IntakeResult, EligibilityResult, HumanApprovalSignal, and WorkflowResult. Enumerate terminal states. Decide which fields are facts, proposals, and authorizations.

Done when invalid state cannot cross a component boundary unnoticed.

Implement pure business rules

Write return-window and refund calculations without Temporal or an LLM. Test boundaries: exactly 30 days, exactly $500, exactly $2,000, unknown issue types, and missing orders.

Done when the policy truth table passes deterministic unit tests.

Add one bounded model capability

Use structured output only for complaint classification. Validate the schema, reject unsupported labels, and retain the original complaint for audit. Build a small evaluation set before adding more prompts.

Done when model upgrades can be compared against repeatable examples.

Wrap uncertainty in activities

Move model calls, database access, messaging, and payment calls behind typed activities. Give each dependency its own timeout and retry policy. Mark permanent failures as non-retryable.

Done when workflow code contains no direct I/O or uncontrolled randomness.

Compose the durable workflow

Orchestrate intake, eligibility, policy gates, refund processing, and customer communication. Keep branches deterministic. Start a workflow with a stable business ID such as customer-support-<order-id>.

Done when killing and restarting the worker does not lose or duplicate completed steps.

Add a real human review protocol

Introduce approval signals, status queries, a durable timeout, reviewer authorization, and duplicate-decision behavior. Record who decided, against which policy version, and why.

Done when a review can outlive every application process involved.

Make side effects idempotent

Derive a stable key from workflow ID plus operation name. Pass it to the refund provider and message service. Reconcile ambiguous timeouts before retrying. Treat deduplication evidence as part of the result.

Done when repeating any activity cannot repeat the business effect.

Test history, failure, and evolution

Add unit tests, workflow environment tests, replay tests against saved histories, and fault injection. Cover worker termination, activity timeout, malformed model output, late approval, and deployment during an open case.

Done when recovery behavior is asserted, not demonstrated manually.

Close the operational feedback loop

Instrument retries, latency, queue delay, human wait time, policy outcomes, and model quality. Route exhausted failures into explicit remediation workflows. Use evidence to tune policies, prompts, and capacity.

Done when the system explains both success and the recovery cost of success.

09 / TAKEAWAY

The agent should never be the only thing that remembers

Long-horizon autonomy is an orchestration problem wrapped around a reasoning problem. Temporal provides durable memory and failure recovery. LangGraph provides bounded cognitive flows. Typed contracts stabilize the seam between them. Deterministic code protects policy. Human signals provide accountable intervention.

The most robust design is not the one that gives the model the most freedom. It is the one that makes every freedom explicit, every side effect replay-safe, every hard rule inescapable, and every recovery path observable.
